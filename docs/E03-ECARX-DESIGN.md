# 星瑞 E03 / ECARX 适配设计

日期：2026-10-10。状态：**设计定稿，未实现功能、未完成实车验收**。

本分支从原版 DiPlay 维护，不把另一套 APK 的全部行为或二进制直接并入源码。
证据见 [实现对比](E03-ECARX-EVIDENCE.md)，验收见 [验收计划](E03-ECARX-ACCEPTANCE.md)。

## 1. 决策

选择 **原版协议核心 + 单 APK 内部 ECARX Module + 经实测的 E03 配置**。

- 拟增加 Android library `:vehicle-ecarx`，随 `:mobile` 打包；不是另装的 APK。
- `main` 保持上游；`codex/e03-ecarx` 维护车型适配及文档。
- 借鉴酷安的直接 ECARX 接入方式，自己重建可维护实现；不复制 APK 中的 SDK 凭据或签名材料。
- 借鉴 carlito 的会话归属、首帧/模式状态分离和焦点协调；不把外部 GD 当成隐含必需品。
- 优先不改变原导航的系统启用状态；是否仍有仪表争用，按 E03 实测决定。
- 方控、仪表和系统独立音量分别验收；某一项通过不替其他项报成功。

这是维护与实现方向的选择，不是“任意自签名 APK 已能完整接入 E03”的结论。

## 2. 三类部署条件互不替代

| 条件 | 说明 | 当前结论 |
| --- | --- | --- |
| 安装身份 | E03 的 APK 安装许可、签名与共享 UID 校验 | 主题只是安装入口，不赋予运行能力 |
| ECARX 接入身份 | SDK 应用授权、服务权限、必要的系统能力 | 自建签名下的实际接受结果待测 |
| CarPlay 连接身份 | 上游 standalone 构建的运行认证输入 | fork / 普通 debug 构建不自动包含它 |

酷安样本声明 system shared UID，且证书与本地系统组件一致。这只能说明证书和清单关系，证书不是签名私钥。
单 APK Module 不会增加权限，也不意味着重现了作者完整构建环境。
身份材料由部署环境提供，保留在仓库外；失败明确记录为安装拒绝、SDK 拒绝或连接认证失败。
不悄悄增加辅助 APK、不沿用样本 AppKey、不把接口异常切换成另一套“看似可用”的实现。

## 3. 源码结构和现有接入点

```text
:mobile                         一个可安装 APK
  └─ :common                    界面、现有会话入口、少量接线
       ├─ :vehicle-ecarx        拟新增 library：E03 具体适配
       └─ :shared               原有协议、解码、音频分类、发送队列

:vehicle-ecarx 可以依赖 :shared 的类型，但不反向依赖 :common。
界面层把现有发送函数和视频出口注入适配 Module，避免循环依赖。
```

现有真实接入点，而不是虚构已有 VehiclePlatform/KeySource 接口：

| 职责 | 保留/复用 | E03 Module 新承担的职责 |
| --- | --- | --- |
| 播放控制 | CarPlayMediaCallback、CarPlayMediaKeys、controller.sendMediaButton | ECARX 媒体源、输入接管、事件规范化 |
| 仪表内容协商 | CarPlayClusterDisplay、AirPlayDisplayConfig、controller 内容切换 | E03 目标屏和可见区域配置 |
| 仪表视频输出 | MediaSink、AndroidMediaSink.setSurface/clearSurface | 原厂模式控制、Presentation 生命周期 |
| 导航提示 | 现有结构化导航信息 | ECARX 导航字段映射及状态协调 |
| 音频输出 | AudioStreamId、AudioChannelMapper、AudioTrack 渲染 | 提供经验证的 E03 用途/stream 路由参数 |

不重写 CarPlay 加密、RTP、iAP2、codec、USB/Wi-Fi 或认证协议。
也不先扩展车辆数据；现有 VehicleStatusProvider 是 EV 模型，不把燃油星瑞伪装成 EV。

### Module / Interface 的具体含义

Module 是有明确职责的源码模块；Interface 是调用方必须知道的使用规则，包含状态、顺序及错误，不只是一串方法名。

| 对外职责 | 小型 Interface 的内容 | 内部隐藏的 Implementation |
| --- | --- | --- |
| 方控输入 | 启动所选输入方式、交付规范化事件、结束占用；说明真实消费结果 | SDK 回调、按键表、配对、跨来源重复事件 |
| 仪表会话 | 请求显示、更新导航、结束会话；输出各阶段状态 | DIM 连接、窗口/Surface、显示源和争用恢复 |
| 音频车型配置 | 提供带验证状态的路由参数 | OEM 属性/用途解析和固件差异 |

这些是拟新增的职责约定，不宣称已经存在对应 Kotlin 类。
SDK 反射和厂商版本差异只放在内部 Adapter；Activity 不负责厂商细节。
发送函数、厂商调用和时钟按需注入，使同一 Interface 可测试。
仅为实际存在的输入/显示差异增加接入位置，不先造通用汽车插件框架或空接口层。

## 4. 飞屏原理：三条链路

```text
操作：三指 / 方控 OK
          ↓ 请求显示

视频：iPhone 导航 App → 仪表视频类型 111 → 原有解码 → Surface → E03 仪表地图区域

控制：ECARX 导航/显示接口 → 原厂显示模式、导航提示、显示源状态

争用：原车导航和 CarPlay 是否抢同一显示区域 → 单独处理，非视频来源
```

111 是 CarPlay 视频类型，不是 Android displayId。
手机提供完整地图视频，是因为 CarPlay 内容由手机生成；车机负责接收、解码和显示。
三指/OK 决定何时显示，并不决定画面来自截图还是手机第二路流。

酷安样本已有三指左滑显示、右滑收起、下滑设置；carlito 使用三指上滑进入投影。
E03 的最终映射以实际收到的手势和键为准，配置明确展示；不把两套同时启用。
若系统先消费了三指手势，应用收到事件的结果单独记录，不预先修改系统全局手势。

### 显示方式选择

- E03 首选酷安证据中的原厂 DIM 协调 + Android Presentation / Surface。
- 借鉴 carlito 的首帧与模式 ready 区分，不默认照搬其 overlay 窗口或闭源 GD 租约。
- 先辨认仪表专用地图区域、名称、显示权限和尺寸，不把任意副屏当作整块仪表。
- 地图安全区按 E03 标定，不继承 BYD 的区域百分比，也不覆盖车速/告警区域。
- 完整地图与转向/距离提示分开开启、分别报告能力；一种失败不暗中换成另一种。
- 手机是否提供仪表 URL、视频开始、首帧渲染和 OEM 模式放行分别记录。

### 生命周期

```text
未请求 → 核对能力 → 协商/申请内容 → 准备 Surface / 厂商模式 → 等待首帧 → 显示
                                      任一环节失败 → 明确失败 → 释放已申请资源
显示 → 用户收起 / 断连 / 会话替换 → 释放显示源、窗口、视频资源 → 核对恢复结果
```

OEM 是否要求模式先于 Surface/首帧，需验证实际顺序；不把其他车型的顺序当成 E03 定律。
“显示成功”要求视频和厂商模式都有证据；窗口对象创建不等于成功。
每个回调带会话归属，旧会话的延迟回调不允许重新占用新会话的显示源。
显示跟随 CarPlay 会话，而不是简单跟随 Activity 的 onDestroy；重建界面与结束连接是两种事件。

## 5. 原导航争用策略

默认仅协调原厂显示接口，不改变 `ecarx.naviservice` 启用状态。
这项默认方向待实车验证，不保证“原导航不开界面就一定不会抢屏”。

酷安不是只暂停原导航：它已经调用 DIM，然后创建第二路窗口，按会话/导航/视频状态另行执行争用处理。
它也已有同步保存原状态、串行执行、核对修改及恢复的实现；保留这些有效做法，不误称为缺失。

若 E03 确认仍会抢屏，提供明确、默认关闭的“会话期间暂停原导航（实验性）”选项：

- 用户明确开启后才改变服务状态，拒绝自动发现冲突后静默停用。
- 修改前持久记录精确原状态和本次操作归属；原本停用则不接管它。
- 退出恢复精确原状态，核对结果；不无条件 enable。
- 记录与当前状态冲突时显式显示，不覆盖用户/其他程序后续改变。
- 只有恢复确认后清除记录；恢复失败与飞屏失败分别显示。
- 进程强杀、断电不保证执行退出回调；下次启动优先核对未完成恢复，不宣称即时保证。
- 暂停只作为经用户选择的兼容策略，不作为“源码已完全掌握原厂调度”的证明。

## 6. 方控：按操作选主通路

推荐初始分工，最终以 E03 事件和消费结果调整：

| 操作 | 首选通路 | 原因 |
| --- | --- | --- |
| 播放/暂停/前后曲 | ECARX 媒体中心语义回调 | 正式媒体源选择、状态同步和后台控制 |
| OK / 仪表切换 | ECARX Input 接管 | 媒体中心回调不承担地图键语义 |
| 普通 Android 键 | 明确选用的输入模式 | 适用于确实由 Android 派发的键 |
| 日志匹配 | 明确选用的诊断/兼容模式 | 被动观察不证明原车独占，不列为默认成功路径 |

对同一操作明确当前主通路；备用观察不发送第二条命令。
如果用户改用 Input 处理媒体键，同步变更媒体中心的发送职责，不让两条路径双发。
不因为 SDK 注册失败自动切到日志，也不因为没接管到键自动宣称标准按键可用。

保留 rawKey、规范键、来源、真实 action、时间和会话标识。语义回调没有 DOWN/UP 时不伪造物理序列。
DOWN/UP/REPEAT 成对处理；长按、双击只有固件有明确事件或经验证的规则时才识别。
时间去重只是补充，避免把用户连续两次正常操作误吞；优先用主通路及可取得的事件标识消除重复。

方控状态分为：注册成功、观察到事件、命令入队、手机实际动作、原播放器未同时动作。
退出释放属于本应用的键占用；无 CarPlay 会话时不残留接管。

## 7. 导航与音乐音量

目标是 **原车可分别调节并保存导航/音乐音量**，而不仅是应用里画两个滑块。

1. 复用协议音频分类，保留音乐、导航、通话、助手等真实角色，不先混成一路 PCM。
2. 使用经验证的 E03 AudioAttributes/stream 参数；usage 1/12 是候选，不是验收答案。
3. 参考 carlito 对厂商用途/配置的读取，记录实际来源、解析与拒绝结果；不盲目采用其他固件的私有 stream 数值。
4. 核对 E03 是否把两类轨道归到不同音量状态；分别调整并用同时播放证明另一类不受影响。
5. 导航播报压低音乐单独控制；由一个会话级协调位置管理，避免 app 和 OEM 同时压低两遍。
6. 通话/助手结束只撤销本次焦点与压低效果，不无条件向手机发送 PLAY，覆盖用户暂停。

若 E03 把用途合并为一个音量组，显式报告“系统独立音量未通过”。
应用内媒体/导航增益可以作为明确命名的另一项功能，但不偷偷替代目标、不伪装成原车独立音量。
压低效果与用户增益分别计算和恢复，不用恢复到 1.0 覆盖用户设置。
不要在无音频策略证据时新增自定义 usage/stream，或修改系统音频策略文件。

## 8. 可维护性与项目价值

- 可重复构建的源码、明确的部署输入、逐项测试和 E03 实车兼容表，而非只发布一个改名 APK。
- SDK 接入集中、会话归属清楚、状态和失败可见，定位问题不依靠关闭原播放器/导航后猜结果。
- 能力诊断在本地查看；日志按用户操作导出并隐藏凭据/标识，不自动扫描上传车辆属性。
- E03 配置区分固件，不通过 Android 9、吉利品牌或某一个属性就宣布所有车型适配成功。
- 对外只安装一个 APK；构建/签名权限不足的事实保留，模块化不用于掩饰它。
- 小型改动接入现有 controller/sink，避免整份复制 Host；同步上游时逐项处理真实冲突。
- 遵守上游 LICENSE 和第三方告知；公开仓库不分发用户 APK、私钥、SDK 凭据或车辆原始日志。

## 9. 实施顺序

1. 确认自建 APK 的安装、ECARX 接入和 CarPlay 连接三类部署条件；只读能力核对，不先改变系统状态。
2. 实现方控媒体源及会话级输入管理，先证明一次操作与原播放器独占。
3. 实现 TBT、仪表专用显示及原厂进入/退出，验证不暂停原导航的争用结果。
4. 完整地图第二路视频：Surface/首帧/模式状态分离，实测手势/OK 与异常恢复。
5. 音频角色、E03 原车独立音量及焦点/压低恢复，全部用实际音量结果验收。

本次分支只有设计文档；上述步骤不是已完成的功能清单。
